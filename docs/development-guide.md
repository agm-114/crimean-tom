# Development guide

This is the handoff document for an agent or contributor entering the project without prior thread context. Read `AGENTS.md` first because its scope and testing rules are mandatory.

## Product boundary

Crimean Tom owns the operations layer between Sea Power battles. The intended loop is:

1. Load the persistent commander and task force.
2. Offer a small set of generated contracts.
3. Generate one complete Sea Power mission from the selected force and contract.
4. Let Sea Power run the battle without live campaign synchronization.
5. Read the native debrief and persistent task-force snapshot.
6. Apply losses, expenditure, salvage, repair, rearm, purchases, group changes, and fatigue.
7. Advance the campaign turn and offer new contracts.

Do not add a campaign server, background war simulation, live unit streaming, a companion process, or a server-authoritative tactical simulation unless the project direction changes explicitly.

The campaign state class is split into `CampaignOperationsState.cs` for lifecycle, `CampaignEconomy.cs` for purchases and salvage, `CampaignReadiness.cs` for groups and refit, `CampaignPersistence.cs` for save access, and `CampaignDebug.cs` for autoresolve. These are partial declarations of the same type, so private state, save keys and external callers stay unchanged.

`Scenarios/ScenarioMissionWriter.cs` contains the fleet-clash writer and shared mission headers, unit counts, startup triggers, and opposed objective declarations. Route and passage writers reuse these helpers but keep their mission-specific victory conditions. Route missions pass their extra protected ships and formations to the common header writer.

`UI/` contains all three windows, shared `NativeUi` styling and campaign-window closing, and `ChoicePicker<T>`. The picker binds string labels to Noesis while keeping values typed in C#, so setup options do not depend on parallel selected-index switches. The scenario families share one setup form but retain their existing options and defaults.

Folders do not change the `CrimeanTom.SeaPower` namespace, reflected type names or deployment locations. The project already enables SDK implicit usings; avoid repeating those imports in every file.

The three longer documents under `docs/` are design references. They describe intended behavior and should not be treated as proof that every feature is implemented.

## Build and deployment

Requirements:

- Windows;
- .NET SDK `10.0.303` or a compatible latest patch selected by `global.json`;
- Sea Power installed, currently developed against `0.8.2-23444+s358`;
- BepInEx and Harmony in the Sea Power installation;
- AnchorChain installed from the Steam Workshop.

Default game path:

```text
C:\Program Files (x86)\Steam\steamapps\common\Sea Power
```

Build from the repository root:

```powershell
dotnet build CrimeanTom.slnx
```

The post-build target copies the assembly to:

```text
Sea Power_Data\StreamingAssets\CrimeanTomOperations
```

It copies the campaign descriptor, roster, art if present, and mission templates to:

```text
Sea Power_Data\StreamingAssets\user\campaigns\crimean-tom-operations
```

Pass alternate paths when necessary:

```powershell
dotnet build CrimeanTom.slnx -p:SeaPowerDir='D:\Games\Sea Power' -p:AnchorChainDll='D:\Mods\AnchorChain.dll'
```

Use `dotnet build CrimeanTom.slnx` for the compile check. Runtime changes must also be checked in the installed game using the manual verification steps below.

## Runtime flow

At startup, `Plugin.TriggerEntryPoint` writes the roster, installs all Harmony patches, writes the direct-launch debug scenarios, and logs the mod version and assembly path.

The campaign uses four always-visible native Task Force Mode entries: fleet clash, route escort, route interdiction, and strait passage. Selecting an entry shows the turn's offer in its native briefing, including region, enemy coalition, broad capability estimates, protected-group variant, payment and salvage terms. `CampaignContractOffers` generates opponents from a saved campaign seed, turn and mission index. The four entries include small, medium and large jobs. Their enemies do not scale with the player's deployment. Reopening an entry or reloading the same campaign does not reroll its terms. Advancing the turn refreshes offers. This is still the native four-entry screen, not a separate contract-board UI.

Immediately before Sea Power's `LinearCampaignTaskForceMissionGenerator.TryGenerate` runs, `CampaignScenarioGenerator` replaces the selected installed template using that offer and the actual launch snapshot. The player's force replaces one side of the predetermined matchup. Campaign seas default to state 1, traffic is off and there is no deadline. Standalone skirmish balancing and setup options are unchanged.

Sea Power's native generator then adds the persistent player ships, aircraft, damage, ammunition, crew state, and `CampaignTag` instance identifiers. `CampaignMissionData` matches those identifiers to the saved template plan, remaps objective references, and restores tactical groups and orders within each campaign group. Convoy and air formations are retained. Passage missions receive waypoints into the exit area after this mapping. Generation or validation errors block launch through the native warning dialog.

After battle, `LinearCampaignTaskForceDebriefViewModel.SaveDebriefSnapshot` is the handoff point. `CampaignOperationsState.RecordBattle` reads the native hostile-kill records, awards salvage shares, creates market offers, advances fatigue, and marks management as pending. Closing the debrief opens `CampaignManagementWindow`. Attempting another mission while management is pending opens the same window and blocks the launch.

Finishing management clears Sea Power's per-mission one-time application markers for the completed reusable mission index, resets that mission's completion state, advances the campaign turn, and saves the campaign.

Pressing F8 on the Crimean Tom campaign map opens `CampaignAutoresolveWindow`. It can write a deterministic native-shaped victory or defeat debrief for any of the four contracts and then enters the same `RecordBattle` and management path used after a tactical battle. This is a campaign-layer diagnostic tool: it deliberately does not simulate tactical damage, ammunition expenditure, combat duration, or friendly losses.

## Persistent state

Crimean Tom stores its state in Sea Power's existing `LinearCampaign.PersistentData` dictionary. Current keys are:

- `CrimeanTomTurn`
- `CrimeanTomSalvageShares`
- `CrimeanTomActiveMission`
- `CrimeanTomPendingBattle`
- `CrimeanTomRecordedBattle`
- `CrimeanTomMarketOffers`
- `CrimeanTomClaimedSalvage`
- `CrimeanTomGroupAssignments`
- `CrimeanTomFatigue`
- `CrimeanTomAutoresolveCounter`
- `CrimeanTomContractSeed`
- `CrimeanTomFirstSortie`

Unit assignments and readiness delays are keyed by Sea Power's persistent instance ID, not class name. Moving between Group 1, Group 2 and Reserve is free and does not change readiness. Recovered units enter Reserve with two refit turns; purchases enter Reserve with one workup turn. They can be assigned to an active group immediately but cannot deploy until ready. Combat does not add operational fatigue yet. The existing `CrimeanTomFatigue` key now represents acquisition/refit delays only.

Reserve and refitting ships never deploy. If all owned hulls are unavailable, launching opens port management so the player can assign ready reserves or wait one turn for workups. Waiting grants no points, salvage or fresh market stock. It advances the turn and contract offers, and is disabled when there are no outstanding workups.

Hull purchasing through the native builder closes after the first sortie. Native aircraft purchasing, repair, rearm and loadout preparation remain available. The post-battle market offers two distinct ship classes at list price with the saved commander discount for eligible national variants. Unclaimed offers expire on finishing management.

Contract payment is `size base + ceil(enemy list value * 0.15) + family premium`. Size bases are 25/40/60, premiums are 0 for clash, 5 for route operations and 10 for passage. Victory also increases point cap by 10/20/30 and grants salvage shares equal to half payment, rounded up. Draws and defeats grant no contract payment, cap increase or salvage shares. Native CSAR rewards and civilian penalties remain separate. Victory can award salvage shares even without kills. At most one destroyed hostile hull may be recovered per battle, at half its list value in shares, rounded up. Surviving enemy register rows are not eligible. Unspent shares carry forward; unclaimed hulls expire.

`RequiredResult=CompleteDefeat` is intentional: the native game otherwise refuses to write failed-battle debriefs. `CampaignPatches` gates both debrief reward reads and the shared native reward application method, including the earlier post-state writer. It disables the campaign-map fallback payment. Do not replace this with a higher RequiredResult and lose defeat persistence.

Campaign fleet clashes use per-hull one-shot destruction triggers to add undiscounted ship value to native variables. A side breaks at 75% lost value. `CampaignValueObjectives` writes these triggers before native renumbering. Passage designates the most valuable hulls covering at least 60% of fleet value; every designated hull must reach the exit, and losing any one fails the passage. Escorts still receive exit routes. Convoy objectives remain cargo-count based.

## Native API inspection

Sea Power campaign types are not all public. The integration therefore uses Harmony and `AccessTools` against the installed assembly:

```text
Sea Power_Data\Managed\Seapower-Scripts.dll
```

Important types:

- `SeapowerUI.ViewModels.LinearCampaignTaskForceSaveManager`
- `SeapowerUI.ViewModels.LinearCampaignTaskForceDebriefViewModel`
- `SeapowerUI.ViewModels.LinearCampaignTaskForceMissionGenerator`
- `SeapowerUI.ViewModels.LinearCampaignMapViewModel`
- `SeapowerUI.ViewModels.LinearCampaignTaskForceBuilderViewModel`
- `SeaPower.LinearCampaign`
- `SeaPower.LinearCampaignMission`

Use `ilspycmd` to verify signatures against the installed game before changing a reflected or patched member. Examples:

```powershell
ilspycmd -t SeapowerUI.ViewModels.LinearCampaignTaskForceSaveManager 'C:\Program Files (x86)\Steam\steamapps\common\Sea Power\Sea Power_Data\Managed\Seapower-Scripts.dll'
ilspycmd -t SeaPower.LinearCampaignMission 'C:\Program Files (x86)\Steam\steamapps\common\Sea Power\Sea Power_Data\Managed\Seapower-Scripts.dll'
```

Native state lookup assumes increasing mission indexes. We store the latest result for each surviving ship under `TaskForceMode_CrimeanTom_UnitState_<instanceId>`, including its damage child sections. The `TaskForceMode_` prefix lets the native save/load code preserve these records. The latest-state hook directs both native repair and launch preparation to them, so playing contract 4 then contract 1 carries forward the same ship state.

Only after management completes, clear both `Mission_<index>_*` and `TaskForceMode_Mission<index>_*`, including old launch/post snapshots and completion-reward flags. Remove the index from the three native record sets as well. Do not delete the current roster or the latest per-ship state. Real debrief salvage sections use `Mission_<index>_TaskForceDebrief_Kill_<row>`. The debug writer must use that exact schema.

1. Start `Crimean Tom Operations` from Campaigns.

3. Launch each contract family at least once.
4. Confirm only ready, non-Reserve units deploy and saved groups appear naturally.
5. Finish a battle and close the debrief.
6. Recover one eligible enemy unit, buy one market unit, move a unit, and finish management.
7. Confirm damage, ammunition, losses, points, salvage, groups, and fatigue survive a save/load.
8. Launch a second mission using the same contract entry and confirm debrief effects and rewards apply exactly once again.
9. Compare offer terms before and after changing deployment; confirm the same enemy force launches and a larger fleet earns no automatic enemy increase.
10. Verify victory and defeat payments, reject a second salvage claim, and confirm native hull buying is locked after the first sortie while aircraft and preparation still work.
11. Check free group moves, Reserve exclusion and waiting out acquisition workups when no active hull is ready.
12. In fleet clash, compare a capital-ship loss with a cheap escort loss. In passage, verify losing a designated ship fails even if enough cheap escorts escape.

For a fast management-layer check, start a Crimean Tom campaign, press F8 on the campaign map, and autoresolve a victory. Exercise salvage recovery, a market purchase, and a group move, then finish management. Run a second autoresolve as a defeat to verify turn advancement, fatigue countdown, market refresh, and the absence of fabricated salvage. This does not replace a real-battle debrief test.

Close an agent-launched game after testing unless the user asks to keep it open.

## Known risks and next work

- The management loop has passed a native-UI, two-turn autoresolve test. A two-battle test using real tactical debriefs and a save/load boundary is still required.
- The latest-state and mission-reference fixes still need full native battle/debrief/save/load verification.
- The campaign shows four native contract nodes with fixed-per-turn briefings rather than a dedicated contract-board UI. Confirm offer text, payment and actual opponents agree in a real launch.
- Fixed threat bands and payment rates need playtesting against actual fleet costs. Buying stronger ships is intended to make existing jobs easier.
- The campaign map preview comes from minimal source templates and may not reflect the final randomized battle until launch.
- Fatigue filtering occurs in the launch snapshot, so earlier native UI may still preview the full owned force.
- Market offers are ships only. Submarines can appear in salvage if the debrief records them.
- The latest design adjustments still need full UI and real victory/defeat payment checks.
- Carrier aircraft, route-operation behavior, friendly AI detachments, and group orders need native gameplay verification after any generator change.
- Reflected and patched members are version-sensitive. Recheck them whenever Sea Power updates.

Keep fixes bounded. Prove one complete real-battle campaign cycle before adding more contract families or deeper management systems.
